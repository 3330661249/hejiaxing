# PM Workbench：让需求结论能回到访谈原话

> **案例性质**：个人制作的独立、本地、确定性工作流原型。以下访谈完全虚构，演示没有调用模型、处理真实用户资料，也没有接入 DeepSeek Harness。原型仓库保持私有；本页重新撰写案例，不公开私有源码或历史研究材料。最后核对：2026-09-23。

## 我想验证的产品问题

产品经理从访谈记录写需求时，容易把受访者说过的话、自己的解决方案和缺少依据的推断混在一起。这个原型验证一条更谨慎的路径：**先看到原话，再人工决定需求与优先级，最后生成可追溯的 PRD 草稿**。这是我设定的演示任务，不是对真实团队效率或客户痛点的实测结论。

成功标准很具体：候选卡能定位到原文；无引用推断不能进入 PRD；纳入与优先级由人决定；修改已纳入需求后，旧 PRD 预览必须失效。

## 一次本机演示记录：资料完全虚构

我输入了两句专为本案例编写的合成访谈：

> 受访者：周会前我总要在三份访谈记录里找原话，很难确认需求从哪里来。
>
> 受访者：如果能先核对原句和材料位置，我再决定是否纳入本期。

本地固定规则读取前两段原文，生成两张带原文位置的候选卡，并固定增加一张“补充访谈覆盖范围”的无引用推断卡。它没有理解访谈含义，也没有让模型判断优先级。我在界面里把第一张卡人工改为“为需求卡保留原文定位”，写明“保留原文和材料位置”是**待验证的产品方案**，不是受访者原话；然后将它纳入本期，并拒绝无引用推断卡。

| 本机操作 | 观察到的行为 | 产品含义 |
| --- | --- | --- |
| 查看候选卡 | 两张卡显示原句及其在材料中的位置；第三张明确标为无引用推断 | 让使用者看到证据与推断的差别 |
| 人工纳入第一张，拒绝无引用卡 | “已纳入 1 条有原文引用的需求”；无引用卡没有“纳入”选项 | 生成结果不能代替范围决策 |
| 生成 PRD 预览 | 只出现这 1 条已纳入需求、原文和人工理由；目标用户、成功指标仍标“待产品经理补充” | 不为未知信息补造结论 |
| 返回修改该需求的优先级，再进入 PRD | 原预览撤下，需要重新生成 | 避免把改动前的草稿当作最新版本 |

这些行为来自本机实际操作；它们证明了这条**演示工作流**能运行，不证明真实用户愿意使用、节省时间或提高需求质量。

## 三个关键取舍

1. **引用完整性先于生成速度。** 需求卡保存原文片段及位置，导出前会重新校验片段与材料是否一致。这样至少能发现引用错位或被改坏；“引用存在”仍不等于“需求解释正确”。
2. **无依据推断留在决策台，不进入正式草稿。** 原型允许看到并暂缓或拒绝这张卡，但不允许将它标成已纳入。只有带引用、且经人工纳入的卡会进入 PRD。
3. **旧产物随有效改动失效。** 改项目名、材料或需求内容后，已生成的 PRD 预览被撤下；无变化的重复操作不会清空它。这把“重新确认”做成实际状态行为。

## 目前还不能证明什么

最重要的失败边界是：**引用文字真实存在，但人工改写的标题或描述仍可能曲解原话**。当前程序校验引用位置和纳入规则，不自动判断整条需求是否受到原文的语义支持。若有人把上面的访谈写成“用户要求全自动生成完整 PRD”，仅靠引用完整性无法识别这个跳跃；这需要人工复核，也应成为以后接入模型时的独立评测项。

原型只在浏览器当前页面保存状态，刷新即丢失；候选卡由固定规则生成，尚无模型需求抽取、真实访谈处理、Harness 宿主集成或生产持久化。PRD 中的目标用户、目标和成功指标未由演示资料确定，因此保留空位。不能把本案例写成已上线的 AI 插件、自动 PRD 系统或业务提效案例。

## 验证范围

我在 2026-09-23 用 Node.js 24.14.0 执行私有原型的类型检查和测试，结果为 **76/76 通过**；随后在本机浏览器走完上述材料、需求、优先级和 PRD 流程，并观察到修改优先级后旧预览消失。私有仓库不对访客开放，所以这不是一份可由公众独立复跑源码的开源案例。公开的是合成输入、可追问的产品规则、观察结果与限制；下一步应补“有引用但解释不成立”的反例和人工语义复核记录，再决定是否开发公开的独立演示。
